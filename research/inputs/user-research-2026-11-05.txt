# Экосистема для «Авито-мастера»: open source, MCP, парсеры, ИИ-агенты, оценка цены и автоматизация чатов

По состоянию на **5 ноября 2026 года** экосистема вокруг Авито уже заметно ближе к тому продукту, который вы описываете, чем может показаться. Есть отдельные зрелые компоненты для поиска и мониторинга объявлений, браузерные MCP-серверы, которые позволяют LLM работать с личным аккаунтом почти как человеку, инструменты анализа цен, проекты с ИИ-скорингом выгодности, агенты для переписки и готовые коммерческие scraping API. Но я не нашёл одного зрелого open-source проекта, который одновременно качественно выполнял бы весь цикл **«найти → нормализовать характеристики → определить справедливую цену → заметить недостающие данные → спросить продавца → торговаться → следить за ответами → принять решение»**. Именно объединение этих компонентов выглядит основной возможностью для вашего продукта. citeturn465272view0turn465272view2turn906400search7turn939855search2

## Что Авито действительно позволяет через API

Важная поправка к исходной гипотезе: утверждение «у Авито вообще нет API» сейчас неверно. У Авито есть достаточно большой **Business API**, включающий работу со своими объявлениями, статистикой, заказами, продвижением и Messenger API. Messenger API умеет получать чаты и сообщения, отправлять сообщения и изображения, работать с webhook-событиями и рядом других функций. Однако это API прежде всего для работы **со своим бизнес-аккаунтом**, а не публичный Search API для произвольного поиска чужих объявлений по всему Авито. citeturn701317search0turn701317search1turn178668search3

Для вашего сценария это принципиальное разделение:

| Задача | Официальный API | Что обычно используют вместо него |
|---|---|---|
| Читать свои объявления | Да | API |
| Читать свои чаты | Да, при наличии доступа к Messenger API | API / браузер |
| Отвечать в своих чатах | Да | API / браузер |
| Получать webhook новых сообщений | Да | API |
| Искать произвольные объявления как покупатель | Публичного Search API нет | scraping / браузер / hosted scraper |
| Открывать карточки чужих объявлений | Не как публичный каталог API | scraping / browser automation |
| Работать с избранным обычного аккаунта | Не основной сценарий Business API | браузерный MCP |
| Писать продавцу как обычный покупатель | Не типичный сценарий Business API | браузерный MCP / automation |

В категориях «Товары» и «Работа» Messenger API сейчас привязан к подписке уровня «Максимальный», а для «Услуг» документация указывает «Расширенный» или «Максимальный». Это ограничение важно, если вы будете строить продукт на официальной стороне API. citeturn906400search2turn906400search1

Сам Авито официально описывает интеграцию Messenger с Jivo, amoCRM, Битрикс24 и Callibri, то есть сама идея внешнего программного интерфейса к чатам полностью штатная для бизнес-сценария. citeturn906400search0

## Оценка реальной стоимости и поиск недооценённых объявлений

Это та часть, где готовых универсальных решений значительно меньше.

**nfilin480/carPrice_pred** объединяет парсер Авито с ML-предсказанием цены автомобиля. Проект специализирован под автомобили, но архитектурно это ровно нужный вам паттерн: собрать comparable listings → построить признаки → regression model → сравнить прогноз с asking price. citeturn939855search0

**Daniil-Solo/Avito-analytics** строит модель оценки квартир в Перми на данных Авито и добавляет не только параметры квартиры, но и признаки окружения: образовательные и медицинские учреждения, общепит, расстояние до центра, координаты. citeturn939855search2

**Zzema/avito_nedvizhimost_analyse** прямо описывает ваш сценарий: периодически собирать объявления, прогнозировать стоимость и искать варианты, цена которых заметно ниже прогнозной. citeturn939855search3

**DynamicPricing** работает с собранными с Авито данными московских новостроек и исследует модели цены и спроса вместе с dynamic-pricing / multi-armed-bandit подходом. citeturn939855search4

**Avito Max Parser** уже вводит практический «scoring выгодности» по цене объявления, данным продавца и risk-signals и позволяет дополнять его LLM-анализом. citeturn939855search6

Интересно, что hosted scraper TopAPI уже возвращает `pageMedianPrice`, флаг `underpriced`, историю переоценки и старую цену, то есть даже простейшую baseline-оценку можно получить без обучения ML-модели. citeturn486019search5

Мой вывод на основе этих проектов: **не стоит просить LLM непосредственно угадывать «справедливую цену»**. Для production-системы лучше сделать отдельный Valuation Engine. Он должен сначала определить категорию и canonical product — например, `iPhone 15 Pro / 256 GB / состояние хорошее / Москва` — затем собрать максимально похожие comparables, исключить выбросы и подозрительные объявления, нормализовать по состоянию, комплектации, географии и возрасту объявления, применить больший вес к свежим объявлениям и вернуть не одно число, а диапазон вроде `fair_value = 82–87 тыс. ₽`, `asking = 72 тыс. ₽`, `discount_to_market ≈ 15%`. Это направление напрямую поддерживается найденными Avito price-analysis и ML-проектами. citeturn939855search0turn939855search2turn939855search3

Для универсального продукта поверх разных категорий я бы использовал два уровня: **comparable-based estimator** как универсальный baseline и отдельные ML-модели для категорий, где достаточно данных — автомобили, недвижимость, смартфоны, ноутбуки, фотооборудование. Это также позволяет объяснять пользователю оценку: «сравниваю с 34 аналогичными объявлениями, медиана 84 500 ₽».

Есть ещё полезный источник старых данных: официальный Kaggle **Avito Demand Prediction Challenge** содержит миллионы параметров объявлений с текстом, ценой, категорией и изображениями, хотя это исторический датасет 2018 года и поэтому он подходит скорее для разработки feature engineering, embeddings и моделей качества объявления, чем для актуальной цены. citeturn939855search9turn939855search10

## ИИ, который задаёт вопросы продавцу и торгуется

Технически эта часть уже почти решена существующими проектами.

`avito-personal-mcp` умеет дать AI-клиенту поиск, карточку объявления, чат, историю сообщений и отправку сообщения от личного аккаунта. Особенно удачно, что отправка сделана через preview + confirmation token: LLM может составить сообщение, но фактическая отправка является отдельным действием. citeturn690441search0

`ermizin/avito-mcp` идёт ещё глубже: LLM видит браузер, элементы страницы и карточки, умеет вводить текст и работать с формами, а необратимые действия требуют явного подтверждения. CAPTCHA проект намеренно передаёт человеку, а не пытается решать автоматически. citeturn906400search7

`aurusxd/avito-ai-agent` демонстрирует уже полноценный multi-stage conversation flow: разные стадии сообщений, анализ входящего ответа с помощью OpenAI/DeepSeek, классификация `interested / neutral / negative` и хранение истории. Хотя проект ориентирован на лидогенерацию со стороны продавца, state-machine можно практически зеркально использовать для роли покупателя. citeturn807983search12

`air_avito` показывает более «официальную» архитектуру AI-ассистента: Messenger webhook → AI pipeline → ответ обратно в Avito, плюс operator handoff. citeturn906400search8

Из этих проектов следует довольно ясная архитектура вашего переговорщика. После разбора объявления агент формирует **Missing Attributes**. Например, для ноутбука: неизвестны battery health, количество циклов, состояние экрана, ремонт, комплект, серийный номер; для автомобиля — VIN, владельцы, ДТП, окрасы, обслуживание; для камеры — shutter count. Далее агент задаёт только вопросы, которые реально меняют оценку или риск. После ответа пересчитывается valuation и определяется диапазон торга.

Я бы представлял состояние сделки примерно так:

`DISCOVERED → ANALYZED → MISSING_INFO → CONTACTED → ANSWER_RECEIVED → REVALUATED → NEGOTIATING → AGREED / REJECTED / HUMAN_REVIEW`.

Для торга LLM нужен не промпт «сторгуй дешевле», а ограничения: `initial_offer`, `target_price`, `absolute_max`, аргументы для торга, запрещённые утверждения и критерий передачи человеку. Такая схема гораздо лучше контролируется и делает действия агента воспроизводимыми.

## Как я бы собрал ваш продукт из уже существующих компонентов

После исследования оптимальная схема выглядит не как один бот, а как несколько независимых слоёв.

**Discovery Layer.** Сохранённые поисковые профили: категория, регион, цена, ключевые параметры, стоп-слова. Для собственного хостинга наиболее сильная отправная точка — `Duff89/parser_avito` или `Egor01KKK/avito-parser`; если инфраструктуру парсинга поддерживать не хочется — API.SH или один из Apify actors. citeturn465272view4turn802195search2turn486019search10turn486019search5

**Normalization Layer.** LLM переводит хаотичные заголовки и описание в каноническую schema: `brand`, `model`, `generation`, `year`, `condition`, `configuration`, `defects`, `location`, `seller_type`, и создаёт `missing_attributes`. Для фотографий можно позднее добавить vision model. Подобный подход с текстовыми и визуальными признаками уже используется в ML-проекте SmartPropertyScraper, хотя тот работает с Cian, а не Avito. citeturn939855search5

**Valuation Layer.** PostgreSQL хранит historical listings и price snapshots; estimator выбирает comparables и считает median/quantiles, затем category model корректирует цену. Реализации Avito-analytics, carPrice_pred и underpriced scoring дают хорошие референсы. citeturn939855search0turn939855search2turn486019search5

**Opportunity Score.** Я бы считал не только discount-to-market, но и ликвидность, свежесть, seller reputation, полноту данных, риск мошенничества, историю снижения цены и estimated resale margin. Именно к такой модели уже приближается Avito Max Parser. citeturn939855search6

**Conversation Layer.** Для обычного аккаунта наиболее интересны `avito-personal-mcp` и `ermizin/avito-mcp`; для аккаунтов с бизнес-доступом — официальный Messenger API через `elchin92/avito-mcp` или собственную реализацию по образцу `air_avito`. citeturn690441search0turn906400search7turn906400search5turn906400search8

**Negotiation Engine.** Здесь почти нет готового хорошего open source. Это, вероятно, ваш основной differentiated IP: агент знает valuation, неопределённость, недостающие характеристики, историю разговора, максимум бюджета и аргументы. Он не просто генерирует текст, а выбирает очередное действие: `ask`, `clarify`, `offer`, `counteroffer`, `wait`, `reject`, `escalate_to_human`.

**Memory/Deal Workspace.** На каждый лот стоит хранить структурированное досье: исходную карточку, снимки цены, comparables, оценку, фотографии/embeddings, seller profile, вопросы, ответы, историю торга и финальное решение. Тогда агент сможет сказать: «из 17 просмотренных MacBook этот второй по выгодности; продавец подтвердил 88% battery health, поэтому после корректировки справедливая цена снизилась с 73 до 69 тыс.».

## Что уже готово, а где остаётся настоящая продуктовая возможность

По результатам поиска картинка довольно чёткая.

**Поиск и парсинг — уже commodity.** Есть десятки open-source парсеров и несколько коммерческих API. Собственный scraper имеет смысл только если стоимость hosted providers станет критичной или вам понадобятся уникальные данные. citeturn807983search6turn486019search10turn690441search4

**Мониторинг новых предложений — практически готов.** Duff89, Egor01KKK, Scanurik, Apify actors и другие уже умеют новые объявления и price changes. citeturn802195search0turn802195search2turn486019search7turn486019search5

**LLM ↔ Авито через браузер — тоже уже существует.** Именно появление MCP-проектов `avito-personal-mcp` и `ermizin/avito-mcp` существенно меняет картину: вам необязательно писать собственный Playwright controller с нуля. citeturn465272view2turn906400search7

**Автоматизация переписки уже существует, но в основном со стороны продавца.** `air_avito`, `MyAlert`, `aurusxd/avito-ai-agent`, BotMan и коммерческие CRM-интеграции решают отдельные части задачи. citeturn906400search8turn802195search9turn807983search12turn906400search11

**А вот хороший AI-buyer / AI-avитолог практически пустая ниша.** Я не нашёл зрелого open-source продукта, который связывает в единый контур comparables, справедливую цену, семантическое сравнение объявлений, выявление недостающих характеристик, диалог с продавцом и управляемый торг. Существующие проекты дают почти все инфраструктурные детали, но reasoning layer остаётся фрагментарным. Это вывод из рассмотренных репозиториев и сервисов, а не утверждение, что такого частного закрытого продукта нигде не существует. citeturn939855search6turn690441search0turn807983search12turn939855search2

С точки зрения скорости разработки я бы **не начинал с написания ещё одного парсера**. Самая сильная стартовая комбинация выглядит так: `Apify/API.SH или Duff89` для discovery + собственная БД исторических цен + category-aware valuation engine + `avito-personal-mcp`/`ermizin` для покупательских действий + отдельный Negotiation Agent с обязательными лимитами и подтверждением значимых действий. Это позволит сосредоточить разработку именно там, где сейчас меньше всего готового open source: на качественном сравнении лотов, объективной оценке цены и автономном, но контролируемом торге. citeturn486019search10turn465272view4turn465272view2turn906400search7
